# RTSEngine

Движок для RTS-игр на C++20: от механики Mushroom Wars 2 до StarCraft 2.
Платформы: Windows, macOS, iOS, Android, HTML5 (WebAssembly).

**Статус: этап 1 — детерминированное ядро и первый игровой модуль (GraphWar).** Рендера пока нет:
симуляция работает headless, матчи играют боты, результат проверяется реплеями.

## Быстрый старт

```bash
cmake --preset linux-release        # или: cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build/linux-release
./build/linux-release/rts_tests

# матч бот против бота с записью реплея
./build/linux-release/rts_headless --map content/graphwar/maps/duel.json --seed 7 --record duel.rpl
# проигрывание реплея с проверкой контрольных сумм на каждой секунде
./build/linux-release/rts_headless --replay duel.rpl
```

Запускать из корня репозитория (пути к контенту относительные).

## Архитектура

```
engine/
  core/    Fixed (Q47.16), Vec2/Vec3, Random (PCG32), Hash (FNV-1a), ECS (sparse set)
  data/    JSON-загрузчик (числа → fixed-point без float)
  sim/     Simulation (фиксированный тик, системы, команды), Command, Replay
modules/
  graphwar/  механика Mushroom Wars: здания-узлы, дороги, отряды, башни, апгрейды, ИИ
apps/
  headless/  CLI: матчи ботов, запись/проверка реплеев (основа будущего dedicated-сервера)
content/
  graphwar/  rules.json (все цифры баланса), maps/*.json
tests/       юнит-тесты без внешних зависимостей
```

Слои строго разделены:

| Слой | Знает о | Не знает о |
|---|---|---|
| `engine/core`, `engine/sim` | ECS, тиках, командах | зданиях, юнитах, рендере |
| `modules/*` | правилах конкретного жанра | рендере, вводе, сети |
| контроллеры (ИИ, игрок, сеть) | командах и чтении состояния | внутренностях систем |
| презентация (будущее) | состоянии, `SimEvent`, `alpha()` | — пишет в симуляцию только командами |

### Детерминизм — главное правило

Сетевая игра в RTS строится на lockstep: по сети передаются только команды игроков, а каждый клиент
считает одну и ту же симуляцию. Значит, симуляция обязана давать **побитово одинаковый результат** на
x86/ARM, MSVC/Clang/GCC, в WASM, в Debug и Release. Поэтому в симуляции:

- никакого `float`/`double` — только `Fixed`, `Vec3`; данные парсятся из текста сразу в fixed-point;
- только свой `Random` (PCG32), никаких `std::rand`/`<random>`-распределений;
- порядок итерации ECS определяется только последовательностью операций, не адресами;
- команды внутри тика сортируются по `(player, seq)` независимо от порядка прихода по сети;
- уничтожение сущностей во время итерации — только через `destroyLater()`;
- порядок систем — часть правил игры.

`Simulation::checksum()` хэширует всё состояние; реплей хранит контрольные суммы каждые 20 тиков и
сообщает тик первого расхождения.

**Проверено:** GCC 13 и Clang, `-O0` и `-O3`, нативное 128-битное умножение и портируемая ветка
(та, что будет работать на MSVC) — на 8 матчах контрольные суммы совпали до бита, реплей,
записанный одной сборкой, проигрывается другой.

### Симуляция и рендер

Симуляция идёт с фиксированным тиком (по умолчанию 20 Гц). Рендер работает со своей частотой и
интерполирует между `Transform::prevPos` и `Transform::pos` по `Simulation::alpha()`.
Звуки и эффекты берутся из `Simulation::events()` (захват здания, выстрел башни, стычка и т.д.).

### Команды

`Command` — единственный вход в симуляцию: `type`, `player`, список `units`, `target`, `point`,
`param`, флаг очереди (shift). Команда, отданная на тике T, исполняется на T + `inputDelayTicks`
(маскировка сетевой задержки). Невалидные команды молча игнорируются: они могут прийти от
читера или отставшего клиента.

ИИ — это контроллер, а не система: он читает состояние и отправляет обычные команды. Поэтому
реплеи не перезапускают ИИ, а боты не могут вызвать рассинхрон.

## GraphWar (модуль в стиле Mushroom Wars)

Всё задаётся в `content/graphwar/rules.json`:

- **юниты:** скорость, атака, защита;
- **здания:** рост в секунду, вместимость, множитель защиты, башня (радиус, интервал, урон),
  превращения (`village → village2 → village3`, `village → tower`, `village → forge`) за юниты гарнизона;
- **механика:** нейтралы не растут; гарнизон сверх вместимости тает на 1 юнит/с; отряды идут по
  кратчайшему пути по дорогам; встречные отряды бьются на дороге; бой при штурме считается через
  атаку/защиту и множитель здания.

Карта (`maps/*.json`) — игроки с командами (team), узлы со зданиями, дороги. Есть дуэль и FFA на 4.

## Как добавить новый жанр

1. Создать `modules/<name>/` с наследником `GameModule`: `setup` (загрузка правил и карты,
   регистрация систем), `applyCommand`, `hashState`, `result`.
2. Описать компоненты (простые структуры) и системы (функции, которые работают на `World`).
3. Зарегистрировать модуль в фабрике (`makeModule` в `apps/headless/main.cpp`).

Ядро от этого не меняется. Следующий модуль — `freemove` (свободное перемещение, как в SC2).

## Платформы

`CMakePresets.json` содержит пресеты для Windows (MSVC), macOS/iOS (Xcode), Android (NDK, arm64),
Web (Emscripten). Ядро не имеет внешних зависимостей и не использует платформенный код, поэтому
собирается везде; проверено пока только на Linux (GCC и Clang). Платформенный слой (окно, ввод,
рендер, звук) появится на следующих этапах.

## Дорожная карта

1. ✅ Детерминированное ядро, ECS, данные, команды, реплеи, модуль GraphWar, ИИ, headless-раннер.
2. Платформенный слой и 3D-рендер (кандидаты: bgfx или sokol_gfx + собственный рендер; WebGPU/WebGL2
   для HTML5), камера RTS, интерполяция, выделение, ввод мышь/тач, клиент GraphWar.
3. Модуль `freemove`: сетка проходимости, навмеш/flow fields, локальное избегание (RVO),
   spatial hash, приказы с очередями, способности из данных, туман войны.
4. Экономика и стройка в стиле SC2, технологии, апгрейды.
5. Сеть: lockstep поверх UDP/WebRTC/WebSocket, лобби, обнаружение рассинхрона по чексуммам.
6. Скриптинг (C#), редактор карт, инструменты.

## Известные ограничения этапа 1

- `Fixed` — Q47.16: точность ~1.5·10⁻⁵. Для больших карт с мелкими шагами можно перейти на 20+
  дробных бит (поменять `kFracBits` и прогнать тесты).
- Встречные бои отрядов — O(n²); для тысяч юнитов нужен spatial hash (этап 3).
- ИИ базовый: в дуэли около 40% матчей заканчиваются по лимиту времени, а синий выигрывает
  чаще красного (21:9 на 50 сидах) — вероятно, сказывается порядок обработки игроков внутри тика.
  Будет исправлено при доработке ИИ.
