# Аудит: можно ли собрать любую RTS без пересборки ядра (данные + Lua)

Цель владельца: *«движок, который позволит собрать любую RTS, которая есть или которой нет, без
пересборки ядра — через Lua»*. Этот документ — проверка цели на фактах: что уже расширяется без
компиляции, какие жанры собираются сегодня, где именно не хватает API, сколько стоит Lua по
производительности и что добавить в ядро (один раз, обобщённо), чтобы цель стала достижимой.

Состояние: ветка `master` на `adfbbac` (Lua 5.4, стандартная библиотека на Lua, 18 образцов игр).
Прототипы: `templates/lua_lab` (5 механик, которых нет в C++), бенчмарк: `templates/lua_lab/bench`,
тест: `lua_lab_prototypes` в `tests/tests.cpp`.

---

## 1. Вердикт

**Цель достижима, но не сегодня и не «через один Lua».** Сегодня движок — очень широкая
*библиотека готовых механик в данных* (≈ 50 команд, ≈ 40 видов эффектов, статусы, триггеры,
планеты, генерация карт, оверлеи, постэффекты) плюс Lua как «клей» правил. Этого хватает,
чтобы собрать **20 из 36** проверенных дизайнов полностью (все классические RTS — данными,
часть нишевых — данными + Lua) и ещё 6 — в основном, без одной ключевой черты. Оставшиеся упираются не в «нехватку механик», а в **отсутствие
нескольких обобщённых точек расширения**: Lua не может (1) получить от игрока собственную
команду с данными и нарисовать под неё интерфейс, (2) хранить данные на сущности, (3)
двигать/менять сущности напрямую, (4) завести своё клеточное поле (огонь, жидкость, шум) с
быстрым ядром и отрисовкой, (5) управлять камерой/вводом, (6) задать свой шейдер/материал,
(7) писать ИИ, (8) менять рельеф и слои карты во время матча, (9) двигаться в полном 3D.

Условия, при которых «любая RTS без пересборки» становится правдой:

1. Добавить **10–12 обобщённых API** из §6 (оценка: ~10–14 недель одного инженера ядра;
   первые пять — ~4–5 недель — закрывают большую часть разрыва).
2. Принять правило: всё «горячее» (движение, поиск пути, клеточные поля, проекция снарядов)
   остаётся в C++ как **параметризуемые ядра**, а Lua выбирает и настраивает их. Lua на
   каждый юнит каждый тик — потолок ≈ 1–2 тыс. юнитов на телефоне (§5).
3. Полный 3D (Homeworld) и физика твёрдых тел — отдельные крупные блоки ядра; без них
   «любая» превращается в «любая 2.5D».

## 2. Что расширяется без пересборки сегодня

| Слой | Как | Что можно | Чего нельзя |
|---|---|---|---|
| Правила симуляции (данные) | `rules.json`, `maps/*.json` | типы, оружие, броня, экономика (stock / flow / товары в зданиях), постройка (walk / warp / morph / sidebar), гарнизоны, линии, территория, комнаты, нужды существ, укрытия, подавление, отряды, транспорты, рынок, предметы, циклы дня/сезона, колода карт, раунды, конструкторы юнитов, кампании, планеты и орбиты | новые *виды* поведения сверх списка |
| Способности и эффекты (данные) | `abilities`, `playerAbilities`, `statuses`, `effects` | композиция ≈ 40 эффектов с доставкой projectile / area / chain / channel / line / cone, вложенность, статусы с `tick` / `onHit` / `onExpire` | — |
| Триггеры (данные) | `triggers` | событие → условия → действия, переменные | сложная логика (для неё Lua) |
| **Lua симуляции** | `scripts`, `scriptBudget` | обработчики 13 событий + `every` + зоны + таймеры `game.after`; запросы (юниты, игроки, ресурсы, статы, карта); действия: give/take, spawn/kill, damage/heal, статусы, баффы, приказы, 23 из ≈ 53 команд, способности, переменные, сообщения, победа/поражение, исследования; хук `{"type":"script"}` в **любом** списке эффектов (способность, оружие `onHit`, статус `tick`, ловушка) и в триггерах; `state` сериализуется, хешируется, откатывается; замена модулей стандартной библиотеки (`scripts/std/*.lua`) | см. §6: собственные команды, данные на сущности, позиция/скорость, поля, видимость, рельеф, ИИ |
| Внутренний `rts.*` | доступен скриптам (не документирован) | ≈ 80 низкоуровневых функций стандартной библиотеки (`rts.has_orders`, `rts.territory`, `rts.place_structure`, …) | стабильности не обещано |
| Lua представления | `viewScripts` | события симуляции, `view.on_frame`, запросы `game.*`; вывод: уведомление, частицы, звук | UI-элементы, камера, ввод, рисование, отправка команд |
| Интерфейс | `ui/*.rml`, `ui/*.rcss`, `fonts/` | полная замена разметки и стилей HUD / меню / лобби | модель данных `game` и колбэки фиксированы в C++ (`apps/client/ClientUi.cpp`); новых полей/кнопок с новым смыслом не добавить |
| Оверлеи | `overlays` | кольца, сетки, клетки, линии, текст, иконки, полосы; условия по выделению, клавишам, зуму, **переменным триггеров** (`{var:NAME}`) | предикаты клеток фиксированы (нет «поля из Lua») |
| Частицы, свет, постэффекты | `fx/*.json`, `lights`, `postfx` | эффекты на события, точечные/прожекторные огни, 14 постэффектов | свои шейдеры |
| Модели и материалы | `models/`, `materials.json` | glTF/FBX/DAE/OBJ/3DS/W3D/VOX, PBR-параметры, текстуры, командный цвет, процедурная анимация | **свой шейдер** — нет (шейдеры в C++ GLSL+MSL) |
| Камера | `game.json camera`, триггер `camera` | орто/перспектива, pitch/yaw/зум, планетная камера, катсцены через триггер | управление камерой из Lua, свободная 3D-камера, свои схемы управления |
| Ввод | — | — | раскладки/горячие клавиши из данных, жесты, свои режимы ввода |
| ИИ | `AIConfig` (сложность) | универсальный C++ ИИ подстраивается под данные, кидает способности по `smart` | свой ИИ на Lua, подсказки ИИ для script-способностей |
| Карты | `maps/*.json`, `generate` | ручные и генерируемые (шум, эрозия, реки, биомы, симметрия), планеты, 2D-тайлы | генератор на Lua; изменение рельефа в матче (кроме копания и воронок-укрытий) |
| Сеть, сохранения | — | lockstep + откаты, реплеи, `serialize()` всего мира (включая `state`) | асинхронный / пошаговый мультиплеер, снимки мира из Lua |
| MCP / редактор | `rtsmcp`, окна | ≈ 70 операций: правила, карты, скрипты (`script_write` / `script_check`), матчи, оверлеи, fx, постэффекты, генерация, кампании, скриншоты | — (достаточно для агентов) |

Вывод по слою: **симуляция расширяема хорошо, представление и ввод — почти никак**. Почти
каждая «невозможная» игра в §3 упирается в то, что у неё *свой интерфейс* или *своя
схема управления*, а не в правила.

им нужны не новые механики, а общие точки расширения.

Самые частые недостающие API в матрице: интерфейс/ввод (`G1`, `G2`, `G10`) — 12 строк;
данные и манипуляции сущностями (`G3`, `G4`) — 9; клеточные поля (`G5`) — 5; мир/время/слои
(`G7`, `G9`, `G11`) — 8.

## 4. Прототипы (`templates/lua_lab`)

Игра «Iron and Gold» (как `templates/scripted`) + пять механик, которых нет в C++. Только
публичный Lua API (плюс данные). Запуск: `build/lin/rts_headless --project templates/lua_lab --seed 3`.

| № | Механика | Файл | Результат (seed 3, боты, матч до победы) | Где API не хватило |
|---|---|---|---|---|

Общие наблюдения:

- **«Своя команда из UI» уже возможна в узком виде:** способность игрока/юнита с эффектом
  `{"type": "script"}` = кнопка на панели + точка/цель → функция Lua. Аргументы — только из JSON
  способности, не от игрока. Этого мало для программ, диалогов, торга, редакторов.
- **Хук `script` в любом списке эффектов — сильная точка расширения**: оружие `onHit`, статус
  `tick` (по сути — периодический скрипт на сущности), ловушки, зоны. Через статусы можно
  эмулировать «компоненты», но без своих данных.
- Детерминизм соблюдён без усилий автора: прогоны seed 3 (две разные сборки, по нескольку раз)
  → одна контрольная сумма `e3711427bc9674c0`; тест `lua_lab_prototypes` проверяет поджог,
  перемотку и повтор матча с ботами; суммы seed 1–3 записаны в `tests/checksums/baseline.txt`.
- seed 3 заканчивается победой (743 с), seed 1 и 2 — ничьей по лимиту 1800 с: программы
  юнитов Синих и истощение мешают C++ ИИ довести атаку (тот самый конфликт «скрипт против
  встроенного ИИ», `G8`).
- Ошибки времени выполнения: 0 (после того как `chain_heal` подключили; ссылка из данных на
  неопределённую функцию сообщается при загрузке — хорошо).

## 5. Производительность и детерминизм

Бенчмарк: `templates/lua_lab/bench` (N нейтральных юнитов на поле 128×128, два игрока-бота
со зданием, 60 игровых секунд = 1200 тиков). Время — **процессорное user-время** процесса
(машина была сильно загружена другими сборками, поэтому стена не показательна), лучшее из
повторов. «Lua, мс/тик» = режим − `idle` (та же сцена без работы скрипта).

| N юнитов | idle (C++ без Lua), мс/тик | read | unit | state | order (вкл. C++ пути) | Lua read, мкс/юнит |
|---|---|---|---|---|---|---|
| 100 | 0.34 | 0.43 (**+0.09**) | 0.42 (+0.09) | 0.51 (+0.17) | 0.72 (+0.39) | 0.9 |
| 1 000 | 5.5 | 6.2 (**+0.67**) | 7.1 (+1.5) | 7.0 (+1.4) | 29.4 (+23.9) | 0.7 |
| 5 000 | 29.3 | 34.3 (**+5.0**) | 37.1 (+7.8) | 43.5 (+14.2) | 196 (+166, 20 с) | 1.0 |

Поле `field` (64×64 = 4096 клеток, шаг диффузии каждый тик в `state`): 1.33 мс/тик, из них
Lua ≈ **1.0 мс** (≈ 0.24 мкс на клетку).

Прототипы `lua_lab` целиком (огонь до 300 горящих клеток + 2873 маркер-сущности, истощение,
программы, перемотка, награды): матч 743 игровых секунды — 66–70 с процессора против ≈ 3.5 с
у `templates/scripted` за 490 с; основная цена — маркер-сущности огня в ECS и `state` огня,
сериализуемый каждый тик, т. е. именно то, что закрывают `G5` и `G3`.

Режимы: `read` — каждый тик `game.units{}` + `game.pos` + `game.hp` по всем юнитам; `unit` —
`game.unit(h)` (таблица из 16 полей на юнит); `state` — запись записи на каждый юнит в
`state` (сериализуется и хешируется **каждый тик**); `order` — раз в секунду приказ всем;
`field` — поле 64×64 целых, шаг диффузии каждый тик, хранится в `state`.

Что это значит:

- Бюджет тика при 20 тиках/с — 50 мс на всё (сим + рендер на том же потоке на телефоне/вебе).
  Разумная доля Lua — **≤ 3–5 мс** на слабом устройстве.
- Чтение юнитов из Lua стоит **≈ 0.7–1.0 мкс на юнит** на этой машине (облачный vCPU
  ≈ уровень среднего телефона). Телефон среднего класса медленнее в 1.5–3 раза, WebAssembly —
  ещё в 1.3–2 раза (Lua в wasm — интерпретатор без JIT; LuaJIT не годится: iOS запрещает JIT и
  нужен детерминизм). Итог: **обход всех юнитов каждый тик допустим до ~1 000 юнитов на
  телефоне и ~500 в вебе**; при 5 000 — только раз в 10–20 тиков или в C++.
- Запись в `state` дороже чтения: весь `state` сериализуется каждый тик. Большие таблицы в
  `state` (история, поля) — главный скрытый расход (прототип №4 и №1). Нужна инкрементальная
  сериализация / данные на сущностях (`G3`) и поля в C++ (`G5`).
- Поле 64×64 на Lua с сериализацией ≈ 1 мс/тик — для огня (шаг раз в 0.5 с, разреженно)
  хватает, для жидкости 256×256 каждый тик — нет: нужны C++-ядра.
- Сам C++ с 5 000 юнитами — ≈ 29 мс/тик даже без Lua: для Cossacks-масштаба профилировать
  нужно ядро, а не скрипты.
- Режим `order` показывает, что дорого не Lua, а то, что Lua *заказывает*: приказ «всем идти»
  раз в секунду — 24 мс/тик на 1 000 и 166 мс/тик на 5 000 юнитов (поиск пути и избегание в
  C++). Массовые приказы из скриптов нужно разносить по тикам, а ядру — групповой путь
  (один путь на отряд + строй, как у `kCmdFormation`).
- **Детерминизм:** каждая конфигурация бенча запускалась дважды — контрольные суммы совпали
  во всех режимах; `lua_lab` seed 3 ×2 → `e3711427bc9674c0` оба раза; тест
  `lua_lab_prototypes` сравнивает два прогона с ботами.

### Почему именно этот список

Вместе `G1`–`G5` дают Lua «полный цикл» механики: **ввод** (своя команда) → **данные**
(на сущности или в поле) → **воздействие** (позиция/статы/поле с C++-ядром) → **отображение**
(свой UI). Сегодня в каждом из четырёх звеньев есть разрыв, и прототипы обходили его
костылём (скрытая способность-телепорт, маркер-сущность, таблицы в `state`, захардкоженная
программа). Остальные пункты — «большие оси» (3D, рельеф, время, шейдеры), каждая открывает
свой кластер жанров.

## 7. Рекомендуемый порядок

1. **G4 + G12 + G15** (≈ 2 недели) — дешёвые, без нового формата, сразу убирают костыли из
   прототипов №2–№5 и поднимают потолок производительности.
2. **G3** (≈ 1 неделя) — данные на сущностях; заодно лечит стоимость `state`.
3. **G1 + G2 + G13** (≈ 3 недели) — своя команда, свой UI, свой визуал: открывает все игры с
   особым интерфейсом (программирование юнитов, Majesty, карточные, «временная шкала»).
4. **G5** (≈ 2 недели) — клеточные поля с C++-ядрами и отрисовкой: огонь, жидкость, шум, влияние.
5. **G8 + G10** (≈ 2.5 недели) — свой ИИ и видимость; камера и ввод.
6. **G7 + G16** (≈ 2 недели) — изменение рельефа в матче, генератор на Lua.
7. **G11** (≈ 1.5 недели) — снимки/время; затем асинхронная сеть отдельным проектом.
8. **G6, G9 (слои), G14** (≈ 5 недель) — контроллеры движения, слои и этажи, свои шейдеры.
9. **G9 (объёмное 3D)** (≈ 3–4 недели) — последним: самый дорогой и нужен 1–2 жанрам.

После шагов 1–5 (≈ 10 недель) по матрице §3 в «Я» остаются только Homeworld, физическая RTS
с разрушаемым рельефом, подземные этажи, асинхронный мультиплеер и игры со своими шейдерами.

Правила для каждого дополнения (чтобы «никогда больше не трогать ядро» было правдой):
детерминизм (только `fx`/целые, сортированный порядок), всё новое состояние — в хеш и в
`serialize`, бюджет инструкций распространяется на новые хуки, у каждой «горячей» функции —
C++-ядро и только параметры из данных/Lua, у визуальных — уровни качества и GLSL+MSL, у
каждого API — MCP-операция и описание в `script_api`.

## 8. Как воспроизвести

```sh
cmake -S . -B build/lin -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build/lin -j3
build/lin/rts_headless --project templates/lua_lab --seed 3            # прототипы, лог script: fire/attrition/...
build/lin/rts_tests | grep lua_lab                                      # тест прототипов + детерминизм
build/lin/rts_headless --project templates/lua_lab/bench --map maps/n1000_read.json --max-seconds 60
```

Карты бенча: `maps/n{100,1000,5000}_{idle,read,unit,state,order}.json`, `maps/n100_field.json`
(параметры — переменные `bench_n` / `bench_mode`, задаются триггером карты).
